DeepStream Parser Regression
Engineering review · DeepStream YOLO parser · Jetson Thor class

A plausible AI-style fix that passes its tests and would stall the video pipeline

The scenario: an AI coding agent is asked to "fix the threshold handling and add the missing NMS" (non-maximum suppression, the step that removes duplicate boxes for the same object) in NVIDIA's DeepStream YOLO output parser. The change it typically produces fixes a real defect and passes the unit test, but makes the parser about 490 times slower than NVIDIA's original on a real frame. LOCI catches this from the compiled aarch64 binary, with no Jetson needed, and an acceptable fix takes its place.

How the pieces were made: the defects were found by code review of NVIDIA's published parser during this project; none is reported in the upstream issue tracker (61 issues checked). NVIDIA's original parser is fast. The slow change is a prepared scenario patch (scenario/innocent_edit.patch) that represents what an agent tends to write for this request, not a recording of one specific agent run. It can also be reproduced live with the prompt in PROMPTS.md.

Code: NvDsInferParseCustomYoloV7 in nvdsparsebbox_Yolo.cpp, from NVIDIA-AI-IOT/yolo_deepstream (pinned commit e9b75770). It runs on the CPU after every TensorRT inference.

What the parser does

NvDsInferParseCustomYoloV7 turns the YOLO network's raw output into a list of boxes. DeepStream calls it on the CPU once per video frame, straight after TensorRT has run the model on the GPU. DeepStream finds it through the config line parse-bbox-func-name=NvDsInferParseCustomYoloV7, which is why its name and signature are fixed.

camera frame
   │
   ▼

   │    output: one tensor of 25,200 rows × 85 numbers
   ▼
NvDsInferParseCustomYoloV7   ← this function, on the CPU, every frame
   │    output: boxes {left, top, width, height, class, confidence}
   ▼
nvinfer: drop low-confidence boxes (threshold 0.25),

   ▼
boxes drawn on screen / sent downstream
Why 25,200 rows

For a 640×640 image YOLOv7 predicts on three grids (80×80, 40×40, 20×20 cells) with 3 candidate boxes per cell: 3 × (6,400 + 1,600 + 400) = 25,200 candidates per frame. Almost all are background; on the test clip about 160 pass the 0.25 threshold.

The 85 numbers per row
  • cx, cy, w, h: box centre and size, in pixels of the 640×640 input
  • objectness: how likely the box contains any object
  • 80 class scores, one per COCO class (person, car, bus, …)
TermMeaning
NMSNon-Maximum Suppression. A detector finds the same object many times with slightly shifted boxes. NMS keeps the highest-confidence box and removes ("suppresses") the other boxes of the same class that overlap it too much, so each object is reported once.
IoUIntersection over Union: how much two boxes overlap, from 0 (no overlap) to 1 (identical). NMS removes a box when its IoU with a kept box is above a limit, here 0.65.
ObjectnessThe model's score for "there is some object in this box", before deciding which class it is.
ThresholdThe minimum confidence (here 0.25) a box needs to be kept at all.
Cluster stageDeepStream's own step after the parser that applies the threshold and runs NMS (cluster-mode=2).
TensorRT / nvinferNVIDIA's GPU inference engine, and the DeepStream element that runs it and calls this parser.

NVIDIA's original

third_party/yolo_deepstream/…/nvdsparsebbox_Yolo.cpp, simplified
extern "C" bool NvDsInferParseCustomYoloV7(...)       // entry point DeepStream calls
{   return NvDsInferParseYoloV7(...); }                // just forwards

static bool NvDsInferParseYoloV7(outputLayersInfo, networkInfo, detectionParams, objectList)
{
    if (outputLayersInfo.empty()) return false;        // no output tensor: error
    float* data    = (float*)layer.buffer;             // the 25,200 x 85 tensor
    int dimensions = layer.inferDims.d[1];             // 85
    int rows       = numElements / dimensions;         // 25,200

    for (int i = 0; i < rows; ++i) {                   // every candidate box
        float bx = data[0], by = data[1], bw = data[2], bh = data[3];
        float maxProb = data[4];                       // confidence = objectness only
        int  maxIndex = data[5];                       // a score cast to int; overwritten below
        for (int j = 0; j < 80; j++)                   // best of the 80 classes
            if (score[j] > maxScore) { index = j; maxScore = score[j]; }
        maxIndex = index;
        data += dimensions;                            // next row
        addBBoxProposalYoloV7(bx, by, bw, bh, 1, netW, netH,
                              maxIndex, maxProb, objects); // centre to corners, clamp, keep if >= 1 px
    }
    objectList = objects;                              // every box goes back to DeepStream
    return true;
}

Per frame that is 25,200 rows × 80 class comparisons (about 2 million cheap comparisons) plus about 25,200 box conversions: 0.83 ms on the laptop, and linear, so twice the rows means twice the time.

What is odd about the originalEffect
No confidence threshold in the parserAll ~25,200 boxes are returned every frame and DeepStream filters them afterwards. Correct, but most of the work is spent on noise.
Confidence = objectness onlyThe class score is not multiplied in, so a box that is 90 % "something" and 30 % "person" is reported as person 0.90. The YOLOv7 reference uses objectness × class score.
int maxIndex = data[5];Casts a score to an integer; meaningless, harmless only because it is overwritten later.
No NMSBy design. NVIDIA's README says the post-processor does "not include NMS"; DeepStream's cluster stage does it.
YOLOv4 path, same fileThe real bug: maxIndex starts at -1 and indexes the threshold table without a check.

NVIDIA also ships a CUDA version of this parser (nvdsparsebbox_Yolo_cuda.cu), which is the sample's default. This CPU function is the alternative whose cost NVIDIA's own benchmark table shows at INT8.

The change and the fix

The agent's change (staged scenario)

Correct output, wrong place for the work

  • Fixes a real bug in NVIDIA's code: the YOLOv4 path can read the threshold table at index -1 when every class score in a row is zero (rare, but an out-of-bounds read).
  • Tightens the YOLOv7 path: the original scores boxes by objectness alone and returns all 25,200 to DeepStream, which applies the threshold later. Not a wrong result, but wasteful and unlike the YOLOv7 reference scoring.
  • Adds non-maximum suppression (NMS) inside the parser, run on all 25,200 candidate boxes before thresholding: a full sort plus a box-against-every-box comparison. This is the slowdown; NVIDIA's original has no such loop and runs in under a millisecond.
  • The test feeds 5 boxes, where that costs nothing. A real 640×640 frame has 25,200.
The fix that shipped

Same bug fixes, threshold first

  • Keeps the index guard and the objectness × class-score confidence.
  • Applies the confidence threshold to each row as it is read, so only about 50 boxes survive instead of 25,200.
  • Leaves NMS to DeepStream's own cluster stage (cluster-mode=2, IoU 0.65), which the sample config already enables.
  • Same detections on screen; parser time 0.65 ms, about 21 % faster than NVIDIA's original because it hands on ~50 boxes instead of 25,200.

The code change

Both edits change the same row loop. The difference is the order of the work: the agent's change runs the expensive step (sort and all-pairs comparison) before the cheap filter, and the fix runs the filter first. Both edits also add the YOLOv4 guard if (maxIndex >= 0 && …).

static std::vector<NvDsInferParseObjectInfo> nmsYoloV7(std::vector<...> candidates, float iou)
{
    std::sort(candidates.begin(), candidates.end(), byConfidenceDesc);  // pulls in recursive introsort
    for (size_t i = 0; i < candidates.size(); ++i) {                     // line 255  rows
        if (suppressed[i]) continue;
        kept.push_back(candidates[i]);
        for (size_t j = i + 1; j < candidates.size(); ++j) {             // line 258  × rows
            if (suppressed[j] || candidates[j].classId != candidates[i].classId) continue;
            if (iouYoloV7(candidates[i], candidates[j]) > iou) suppressed[j] = 1;
        }
    }
    return kept;
}

What LOCI did

  1. Matched the real build. LOCI recorded how the project compiles for the Jetson Thor target (aarch64, Neoverse V2 timing model at 2601 MHz). Its own compile came out byte-identical to the production object, so it measured the code that would actually ship.

  2. Measured the compiled binary, not the source. From the aarch64 object it derived timing per execution path, stack frame size, loops and their trip counts, and recursion, without running anything on a device.

  3. Judged it against a written budget. Five rules, drafted from NVIDIA's published frame-rate numbers, turned those measurements into a pass or fail rather than a number to interpret.

  4. Pointed at the cause. It named a new loop over the candidate rows nested inside the existing row loop (loops at lines 255 and 258; the compiler's debug info places their blocks at 259–260) and recursion pulled in by std::sort, which is the design flaw rather than a tuning issue.

What that adds up to

402 ms ÷ 182 million iterations ≈ 2.2 ns per inner iteration on the laptop. That is the 487×: a cheap loop body run 182 million times per frame.

This is why the contract pairs its timing budgets with a structural rule, "no loop over the rows inside the loop over the rows". The ns figure is a floor; the nesting is what predicts the blow-up.

Limits of this evidence

  • The slow change is a prepared, representative patch, not output captured from a specific agent run.
  • Nothing here has run on a Jetson. The laptop timings show the direction and the order of magnitude; the Jetson-class figures are LOCI's estimates.
  • The five rules are a draft. The pass and fail verdicts above are read against them; they become enforced once the repository owner accepts the contract.
  • In the laptop demo, onnxruntime stands in for TensorRT and a Python NMS stands in for DeepStream's cluster stage. The parser in the middle is NVIDIA's C++ code, unchanged apart from the edits being compared.
